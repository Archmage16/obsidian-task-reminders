# Напоминания на Ubuntu с Syncthing

Используемая схема развёртывания: Obsidian на компьютере, Syncthing для двустороннего обмена одним файлом задач и один процесс напоминаний на Ubuntu. Ниже — переносимые команды для этой схемы. После изменения кода или конфигурации доставку, синхронизацию и восстановление проверяют повторно.

На предыдущей проверке развёртывания были подтверждены обе активные и включённые службы, `Linger=yes` и автоматический запуск бота после фактической перезагрузки. Новые функции создания задач и изменения срока подготовлены локально. Пока сервер выключен, их серверная установка и живая проверка ожидают следующего включения.

## Один актуальный файл задач

Syncthing обменивается `Задачи.md` между компьютером и сервером. В этой схеме отдельный экземпляр Syncthing соединён только с известным устройством через частную сеть: глобальное и локальное обнаружение, relay и NAT отключены; web-интерфейс привязан к loopback. В Git не попадают реальные адреса, device IDs, XML-конфигурация и ключи Syncthing.

Файл `.stignore` разрешает только `Задачи.md`: остальные заметки хранилища не передаются этим экземпляром. `deploy/sync_config.py` настраивает выделенную пару при остановленном Syncthing, проверяет устройства и сохраняет исходный XML отдельно. Существующий посторонний экземпляр Syncthing этим скриптом не перенастраивают.

Добавление служебных ID и кнопка «Выполнено» тоже меняют файл, поэтому папки должны быть `sendreceive` на обеих сторонах. Перед включением новой копии сначала дождись завершения синхронизации; не запускай два бота для одного токена. Конфликтные версии сохраняются Syncthing, но не исполняются как отдельные файлы задач: после конфликта сравни содержимое вручную.

Создание из Telegram и изменение срока также записывают серверный `Задачи.md`. Успешный ответ означает «сохранено на сервере»; появление строки или нового срока на компьютере зависит от следующей синхронизации. Для добавления файл должен завершаться вне блока кода: незакрытый блок нужно исправить вручную.

На Linux файловая блокировка advisory. Проверки inode и содержимого выявляют замену файла во время операции, но не дают общей гарантии против приложения, которое перезаписывает файл без блокировки. При занятом или изменившемся файле операция должна повторяться после получения актуальной версии.

## Процесс и данные

Используется непривилегированный пользователь. Код размещается отдельно от состояния; `data_directory` содержит очередь, offsets, служебные статусы и копии Markdown. Каталог данных — только для сервисного пользователя (`0700`); файлы секретов — `0600`. Пути в шаблонах используют `%h`, поэтому реальные домашние каталоги не записываются в репозиторий.

Для системной службы используется один `bot_service.py --watch`, а не отдельные конкурирующие процессы для очереди и кнопок. Перезапуск службы не должен сбрасывать SQLite и offsets. Журнал содержит безопасные коды ошибок, без токена, полного API URL и тел запросов.

## Linux-секреты

Текущий Windows DPAPI blob связан с Windows и текущим пользователем. Его копирование на Ubuntu не подключает бота.

Linux backend использует [Fernet](https://cryptography.io/en/latest/fernet/) для аутентифицированного шифрования токена. Файлы `token.enc` и соседний `.secret.key` принадлежат текущему сервисному пользователю и имеют права `0600`; их папка — `0700`. Backend отклоняет небезопасные права и символические ссылки. Ключ остаётся вне репозитория и папки кода. Если атакующий получает и ciphertext, и ключ, шифрование не защищает токен.

Первичная настройка проходит локально на сервере через скрытый ввод, без токена в аргументах команды, переменных окружения, чате и конфигурации Git. Зашифрованный токен и ключ сохраняются с ограниченными правами; ключ резервируется отдельно. `setup_bot.py` — окно настройки Windows; на Linux используется защищённое подключение ниже.

При смене пользователя службы нужно проверить доступ к ключу и зашифрованному файлу. Ошибка расшифрования должна давать короткий безопасный статус и не создавать незашифрованный запасной файл.

## Установка и подключение

Команды выполняются из папки исходного кода от того пользователя, который будет запускать службу. Нужен Python 3.11+; существующее развёртывание Ubuntu использует системный Python 3.12 и пакет `python3-cryptography` версии 41.0.7. Этот вариант соответствует `/usr/bin/python3` в шаблоне службы:

```sh
sudo apt install python3 python3-cryptography
python3 -c "import cryptography; print(cryptography.__version__)"
cp config.example.json config.json
```

Нужна версия `cryptography>=41`. Альтернатива для другого окружения — `python3 -m venv .venv`, затем `.venv/bin/python -m pip install -r requirements.txt`. При этом все команды проверки и `ExecStart` службы должны использовать именно `.venv/bin/python`, а не системный Python.

В `config.json` укажи реальные абсолютные пути к постоянно обновляемому хранилищу и частной папке данных. Папка данных должна принадлежать сервисному пользователю и иметь права `0700`. Следующая команда запрашивает токен скрыто и создаёт только зашифрованный файл с ключом:

```sh
python3 -c "import json; from pathlib import Path; from getpass import getpass; from secrets_store import save; d=Path(json.loads(Path('config.json').read_text(encoding='utf-8'))['data_directory']); save(d/'token.enc', getpass('Telegram token: '))"
```

Отправь `/start` своему боту и запиши **свой личный chat_id**, который будет владельцем кнопок и получателем сообщений. Не указывай ID группы. Сохрани его отдельно от исходного кода:

```sh
python3 -c "import json; from pathlib import Path; d=Path(json.loads(Path('config.json').read_text(encoding='utf-8'))['data_directory']); n=int(input('Owner private chat_id: ')); assert n>0; p=d/'settings.json'; p.write_text(json.dumps({'chat_id':n}), encoding='utf-8'); p.chmod(0o600)"
python3 -m unittest discover -s tests -v
python3 reminders.py --config config.json --status
```

После остановки прежнего экземпляра проверь ручной запуск и публикацию меню, затем настрой системную службу с тем же пользователем, окружением и конфигурацией:

```sh
python3 bot_service.py --config config.json --menu
python3 bot_service.py --config config.json --watch
```

Закрытие терминала останавливает ручной процесс. Постоянную работу и восстановление после перезагрузки обеспечивает отдельно установленная системная служба.

## Автозапуск и выход из RDP

В `deploy/` находятся шаблоны пользовательских служб `obsidian-tasks.service` и `obsidian-task-sync.service`. Они предполагают код в `~/.local/opt/obsidian-task-reminders`, частную конфигурацию в `~/.local/share/obsidian-tasks/config.json` и отдельную установленную программу Syncthing. Сверь эти пути с выбранной установкой перед копированием.

Шаблон запускает `/usr/bin/python3` и соответствует основной установке через `apt`. Если выбран альтернативный `.venv`, измени `ExecStart` на абсолютный путь к `.venv/bin/python` и запускай тесты тем же интерпретатором. Проверка только из активированной `.venv` не подтверждает работоспособность другого Python в службе.

```sh
mkdir -p ~/.config/systemd/user
cp deploy/obsidian-tasks.service deploy/obsidian-task-sync.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now obsidian-task-sync.service obsidian-tasks.service
sudo loginctl enable-linger "$USER"
```

`enable-linger` позволяет пользовательским службам работать после выхода из RDP и запускаться без интерактивного входа после загрузки системы. Отключение окна RDP само по себе не выключает сервер. Чтобы напоминания продолжались, Ubuntu должна оставаться включённой и не уходить в сон; настройка службы не отменяет сон или выключение системы.

Оба шаблона используют `Restart=always`, задержку 10 секунд и не блокируют будущие попытки после серии ошибок. Явный `systemctl --user stop obsidian-tasks.service` останавливает бота. Постоянные ошибки нужно исправлять по безопасному статусу, а не считать цикл перезапусков нормальной работой. Служба синхронизации восстанавливается независимо от бота.

Для проверки состояния без чтения секретов:

```sh
systemctl --user is-enabled obsidian-tasks.service obsidian-task-sync.service
systemctl --user is-active obsidian-tasks.service obsidian-task-sync.service
loginctl show-user "$USER" -p Linger
```

После перезапуска обеих служб проверь новую тестовую задачу, перенос срока, выполнение из Telegram и обратную отметку в Obsidian. Отдельная проверка после выхода из RDP или перезагрузки подтверждает соответствующий сценарий; включённый unit сам по себе его не доказывает.

Главное меню включает «➕ Добавить задачу» (`/add`), «📝 Задачи» (`/tasks`) и «📅 Дедлайны» (`/deadlines`). В списке задач есть фильтры «Активные», «Выполненные», «Все» и переходы между страницами. Дедлайны показывают исходный срок незавершённой задачи, включая просроченные; задачи без срока идут отдельно. «Проверить связь» отвечает сразу, а «Тест через 1 минуту» проверяет отдельную отложенную отправку. Команды и кнопки разрешены только владельцу в личном чате.

После `/add` укажи название одной строкой до 2000 символов, затем срок в UTC+05: `YYYY-MM-DD HH:MM`, `сегодня HH:MM`, `завтра HH:MM`. Есть быстрые кнопки «Через 2 часа», «Завтра 09:00» и «Без срока». Выбор срока сохраняет сразу. Для существующей активной задачи кнопка «🕒 номер» открывает изменение срока; «Без срока» убирает напоминания. Старое действие не должно перезаписать новый срок, выставленный в Obsidian.

Диалог отменяется кнопкой «Отмена» или `/cancel`. Обычный незавершённый черновик истекает через час; запрос, уже ожидающий записи в занятый файл, автоматически повторяется с тем же ID и переживает перезапуск. Отмена такого запроса не удаляет уже записанную задачу. Если ответ Telegram не доставлен после успешной записи, повторяется подтверждение; задача не создаётся заново в рамках того же запроса.

Названия в черновиках и запросах сохраняются в частной `controls.sqlite3`; эта база содержит пользовательский текст и не должна попадать в Git, журналы, публичные отчёты или синхронизацию хранилища. Права папки данных `0700` и `UMask=0077` службы относятся и к этой базе, а не только к файлам токена.

## Если компьютер или сеть недоступны

Сервер отправляет напоминания по последней полученной версии `Задачи.md`, даже когда компьютер выключен или Obsidian закрыт. Новые строки, удаление, перенос срока и локальная отметка выполнения доходят до него только после возобновления Syncthing. Поэтому отменённая на отключённом компьютере задача может продолжать напоминать до синхронизации. Выполнение кнопкой Telegram действует на сервере сразу; компьютер получит отметку при следующем подключении.

Если сервер выключен, спит или не имеет связи с Telegram, своевременная доставка невозможна. После восстановления очередь и следующее время повтора остаются сохранёнными; программа догоняет без пачки сообщений за каждый пропущенный двухчасовой интервал. Состояние «служба запущена» проверяй вместе с реальной доставкой и актуальностью файла.

## Переключение

1. Подготовить код, рабочую конфигурацию и защищённый Linux backend после входа через RDP.
2. Подтвердить постоянное чтение актуального Markdown и сохранность его содержимого.
3. Остановить локальный процесс, использующий того же бота.
4. Запустить один серверный процесс и проверить отсутствие конфликтующего polling.
5. Проверить создание из Telegram, появление строки в Obsidian, изменение и удаление срока, выполнение и удаление задачи; проверить разрешённые владельцу кнопки. Убедиться, что занятый файл повторяется без дубля и что потеря подтверждения не повторяет запись.
6. Проверить двухчасовой повтор и сохранение следующего времени после перезапуска службы.
7. Перезагрузить сервер и подтвердить автозапуск, доступ к файлу задач и доставку.

Если перенос не удался, сначала остановить серверную копию и только затем возвращать локальную. Одновременная работа двух серверов с одним ботом не допускается.
